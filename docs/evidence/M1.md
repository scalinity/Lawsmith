`src/rendering/backend.ts` and `src-tauri/` are unchanged: Rust stays thin, and native focus comes from the pinned `onFocusChanged` JS API under the existing `core:default` capability. New tokens in `src/style.css`: `--floor`, `--grid-minor`, `--body`, `--danger`.

Choices worth knowing:
- The floor carries the sphere's material (friction 0.6, restitution 0.25), so Rapier's default average combine yields exactly the recipe's contact values. SPEC §2.2 does not name the floor's material.
- A gesture ends on its last valid value. A pointer that reports `buttons === 0` while a drag holds it ends that drag as a release would have (gizmo: commit; orbit: its own `pointercancel` path). Escape, `pointercancel`, a `lostpointercapture` that leaves the drag running, focus loss and a gap cancel instead, restoring the gesture's starting value through a new `putField`.
- The window-drag element over the top 40 px stays the same native `data-tauri-drag-region`, but sets `pointer-events: none` while the law or a gizmo handle lies under the pointer, and for the duration of any gesture.
- Arrows sample the host's own `CompiledField` on a 5×5×5 lattice at local fractions ±0.875/±0.4375/0. The outer layer sits at d = 0.875, where f = 0.25 gives weight 0.5. Scale: 0.05 m per m/s², hidden below 0.05 m/s². Refresh: on each new applied value, at most 30 Hz during a gesture.

## Findings

M0 findings carried by M1:

1. **M0 finding 1, lost pointer-up: open.** M1 adds reconciliation: a drag still held when the pointer reports `buttons === 0` ends as its release would have. No pointer-up was lost in 72 synthetic page drags (M0: about 1 in 6–8). A loss could not be forced synthetically, so the reconcile path has no native evidence yet. The root cause is still unknown. Owner: **M1**, closing on owner check 1.
2. **M0 finding 2, window jump: open, characterized.** One recurrence in 11 drag-region drags (origin landed on the drag's end point) and none in 10 targeted repeats. It has now appeared only under synthetic input, after a recent activation change. M1 did not change the native drag path (`data-tauri-drag-region` → `start_dragging` → tao); M1's yield only toggles the element's `pointer-events`, and the region was hit normally. No fix is claimed. Owner: **M1** for the owner's real-input observation. Proposed: move it to M8, which owns native controls polish, if the owner does not see it; that move needs owner approval.
3. **M0 finding 5, startup compile: open, observation.** Cold 3.06 s and warm 1.98 s with the real M1 scene; no M1 requirement fails. Proposed owner: M9 (performance envelope), pending owner approval; M1 until then.
4. **M0 finding 6, OrbitControls `end` on gizmo release: closed.** TransformControls is constructed first, so its `pointerdown` disables orbit before OrbitControls sees the press. Result: 0 orbit events in 59 gizmo gestures, 0 ownership conflicts, and real orbit drags still log exactly one `end` each.
5. **M0 finding 7, drag strip over the canvas: closed.** The strip yields wherever the law or a handle is under the pointer. A handle placed inside the band was dragged with the window unmoved, and the empty band still moves the window.

New in M1:

6. **Rapier 0.21 caps linear speed at 400 m/s × `lengthUnit`, independent of `dt` and CCD; a force cannot push past it.** This is an effective engine limit absent from the profile record. SPEC §9.3's 1000 m/s stop therefore cannot trigger, and above 400 m/s the adapter's `v_next = v + h·A` (SPEC §9.1) would not hold. M1's scenes run near 10 m/s, and a Vitest characterization test pins the behavior so an engine change is noticed. This needs an owner decision on whether SPEC §9.3 or the profile should state it; it matters by M3, where 200 m/s² laws can reach 400 m/s in about 2 s. Owner: specification owner; proposed unit M3.
7. **Timer resolution is 1 ms in this WKWebView.** Step and edit timings are quantized, so P0 step readings of 1 ms mean under 2 ms. Fine for P0's 2 ms gate; M9's tighter work should account for it. Informational.
8. **No keyboard or numeric editing of law pose or extent yet.** A keyboard user can select the law, enable it, play, step and reset. Editing position, rotation and extent is spatial only. MILESTONES assigns numeric handle equivalents to M3 and keyboard/DOM equivalents to M8; M1 requires no precision panel. Owner: M3/M8 per MILESTONES.
9. **Fixed during dev smoke, before the candidate:** gesture logs passed a `mode` key that `report()` overwrote (renamed `transformMode`); a gesture's final revision applied before release was reported late; the scheduler's own gap pause emitted no `sim-control` line. The gap fix is verified by code and tests only, because no gap occurred while playing in the packaged session.
