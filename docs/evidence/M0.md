## WebGPU qualification

The backend is read after `await renderer.init()` in `src/rendering/backend.ts`, the only module touching renderer internals. It passes only if `renderer.backend.isWebGPUBackend === true` **and** `renderer.coordinateSystem === WebGPUCoordinateSystem`. Both names were verified in the pinned three 0.186.1 source, where `init()` silently swaps in a WebGL 2 backend on failure. After `compileAsync`, a 64×64 render-target readback checks the scene actually rendered.

## Rapier

`initSimulation()` awaits `RAPIER.init()` before creating any engine object. It then configures a throwaway zero-gravity smoke world with the SPEC §9.3 starting profile, steps it once to show the WASM executes, records the effective parameters and frees the world. No stepped engine state is handed to M1. Version 0.21.0 initialized in both modes (9–18 ms dev, 23–33 ms packaged). Effective integration parameters, to pin in M1's profile: `dt 0.008333333767950535` (f32 storage of 1/120), `numSolverIterations 4`, `numInternalPgsIterations 1`, `maxCcdSubsteps 1`, `lengthUnit 1`, `normalizedAllowedLinearError 0.004999999888241291`, `normalizedPredictionDistance 0.019999999552965164`.

## Frame pacing (observation only, not P0)

In the packaged app, 47 of ~50 five-second windows show frame-callback intervals p50/p95/p99 = 17/17–18/18 ms, max 18–19 ms, CPU frame work p95 ≈ 1 ms, at 60 Hz. Startup: renderer init 5–13 ms, Rapier 23–33 ms. The first frame arrives 3.3 s after launch on a cold start and 1.1 s on a later launch. Almost all of that is `compileAsync` and readback pipeline compilation, which WebKit appears to cache between launches. Stalls over 50 ms happen only at startup, during fullscreen transitions, and while minimized (1.9 s gap, when WKWebView suspends frame callbacks).

## Findings and limitations

1. **Intermittent lost pointer-up (open).** With synthetic input, about 1 in 6–8 canvas drags never delivered `pointerup` to the page, even though OrbitControls listens on the document. OrbitControls then stays in a rotate state holding pointer capture, and the next press, even on the drag region, goes to the canvas. One occurrence turned a drag-region drag into a camera flip. A cursor teleport before the press did not explain it (4/4 vs 3/4). The app adds no `preventDefault` or `stopPropagation` to pointer events. The independent review's candidate cause: `drag.js` sends `start_dragging` asynchronously, and tao's `drag_window` starts a native drag from whatever `NSApp.currentEvent` is at that moment, so a late call could swallow a later mouse-up. That does not explain the misses with no drag-region press nearby, so the root cause (WKWebView/WRY/tao or event injection) is still open. M1's pointer-ownership work (SPEC §10.3: release on pointer-up, cancel, blur or lost capture) should end a gesture whose pointer reports `buttons === 0`. Owner check 3 on a real trackpad lost no pointer-up in 16 gestures (6 orbit drags, 10 Move drags). The finding stays open for M1's pointer-ownership work.
2. **Unreproduced window jump.** Once, after an unfocused drag-region drag and an unfocused canvas press, the window ended at (64, 472). Six controlled repeats of the same and neighbouring sequences did not reproduce it. None was reported during owner check 4.
3. **Unfocused dragging.** Tauri documents that an Overlay drag region cannot move an unfocused window. Here it does, in one gesture, with a consistent 6 pt overshoot. `acceptFirstMouse` is left at its default; an unfocused canvas press only activates. Owner check 4 on real input: the window moves and comes to the front on the first gesture. This is recorded as the pinned release's activation behaviour (SPEC §11.1); resolved.
4. **QA sizes unavailable.** This display offers 1168×755 pt, and macOS clamps 1280×800 and 1600×1000 windows to 1168×733. Qualified sizes: 1168×734/733, 930×620 and fullscreen 1168×729. Owner check 1 ran under More Space at 1285×801 and 1601×1008 css; resolved for M0. M2, M4 and M8 need the same setting for their 1280×800 checks.
5. **Startup compile.** First frame takes about 3.3 s. M1 should keep this in view; M0 does not optimize it.
6. **OrbitControls `end` on gizmo release.** OrbitControls also receives the gizmo's `pointerdown` and fires `end` on release with an unchanged camera. It is harmless here; M1's proxy gizmo owns this ordering. The owner session shows it too: each of the 16 gizmo releases also logged an orbit `end`.
7. **The drag strip covers the top 40 px of the canvas.** This is the spec's “unused top whitespace” design: a gizmo handle moved into that band is reachable only after orbiting or Frame. M1 should keep law handles out of the band or revisit its height.
8. **DPR changes between displays at the same window size are untested.** Only one display was available; render size is re-applied on resize and at viewport creation. Deferred by owner decision (2026-10-06) until an iPad is used as a second display through Duet.
