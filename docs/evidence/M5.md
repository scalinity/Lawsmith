## The expression (SPEC §6.3, §15)

**Representation.** Exactly SPEC §6.3's union, as plain frozen data with no closures and no engine handles:

```text
FieldExpression = Primitive
  | { kind: "sum";  terms: FieldExpression[] }                        nonempty, stored order
  | { kind: "gain"; gain: Gain; child: FieldExpression }
  | { kind: "mask"; pose: Pose; region: Region; edgeFade; child: FieldExpression }
Gain = { kind: "constant"; value } | { kind: "triangle"; min; max; periodTicks; phaseTicks }
```

No other key is accepted, at any depth. There is no ingredient-enabled flag: an `enabled` key on a term is refused as unknown (`terms[1].enabled`).

**Limits** (SPEC §15.2), on import and on every live edit: at most 64 nodes per law (leaves and operators alike), depth at most 8 (a primitive alone is depth 1), at most 256 primitive leaves across the scene, and the existing 32 laws, 5 MiB, ID and text bounds. Depth is checked when a node is reached, before any child is read. Every node counts toward the budget, and a terms array longer than 64 is refused by its length. A file's expression goes through the same validator as a live edit, so it never recurses without bound, and an in-memory node that is its own ancestor is refused as "expression contains a cycle". The scene's leaf budget names the law that crosses it. The document checks it against every law's latest submitted value, so two edits waiting for the same boundary cannot pass together.

**Validation** (SPEC §9.3): gain finite in 0–16 (negative refused, so drag cannot become energy injection); a triangle's `periodTicks` an integer ≥ 2, `phaseTicks` an integer in `[0, period)`, `0 ≤ min ≤ max ≤ 16`; mask positions within ±1000 m, rotations finite and nonzero; region dimensions 0.01–100 m; fades 0–1; leaves by their registry entries. Errors name the exact path, e.g. `semantic.fields[2].expression.terms[1].gain.phaseTicks` and `semantic.fields[0].expression.child.region.radius`.

**Canonical form** (SPEC §15.1): quaternions under the existing sign and unit rules (mask poses included), negative zeros removed, directions normalized, sum terms in stored order, and accepted values exact (no quantization). `validateExpression` is idempotent on its own output.

**Capabilities.** A scene declares, sorted and once each, every capability it uses: the support region of every law, and every primitive, operator and mask region anywhere in its tree. A file that uses a nested capability without declaring it is refused (`requiredCapabilities`), as is one that declares an unknown operator (`operator.clamp.v1`). A primitive-only scene declares no operator and re-exports byte for byte as in M4.

## The compiled evaluator (SPEC §6.3, §8)

`compileExpression` runs once per accepted law, on load or on an accepted edit. Nothing is validated or parsed per sample, and nothing is allocated: each `sum` owns one scratch vector.

| Node | Evaluation at law-local r and tick n |
| --- | --- |
| primitive | its registry evaluator; a one-leaf law runs exactly that closure (the tick is the last argument, so a primitive's evaluator is already an expression evaluator) |
| `sum` | A = A₁ + A₂ + …, K = K₁ + K₂ + …, left to right in stored order, starting from the first term; never reordered, reassociated or deduplicated |
| `gain` | g·A and g·K with g = `gainAt(gain, n)`; a zero gain writes exact positive zeros without evaluating its subtree (a constant 0 compiles to that directly) |
| `mask` | w·A and w·K, w the SPEC §7 weight of `Rₘᵀ(r − pₘ)` in its region; the child is evaluated at r, the law-local point: a mask changes support, never a child's frame |

`sampleField` then applies the law's outer support once, to the whole tree, rotates A by the law's rotation and leaves K unrotated. These are the same operations, in the same order, as M3's.

**K ≥ 0.** Every leaf's K is a nonnegative coefficient or zero, gains are ≥ 0, and mask and support weights lie in [0, 1], so every K is nonnegative by construction. A seeded test samples 200 random trees (signed strengths, triangles, nested masks, random rotations) at 10,000 points and ticks, and finds every output finite and every K ≥ 0.

**The tick.** Each consumer passes the tick it explains: the host samples at boundary n, the transition n → n+1 it is computing; the preview at the current tick; a probe advanced after that step at n, its own tick; drawn samples and fixtures at the host's current tick. A tick-dependent law's arrows are resampled when the tick changes, at most at 30 Hz.

## The editor (AC7, AC8)

The ingredient list lives in the selected law's details, below its M3 controls. A one-leaf law keeps its M3 inspector unchanged (kind line and primitive fields), followed by one row: "Ingredients", the Push/Pull/Swirl/Drag shelf, and the line "Add one to combine it with this law's primitive." For a compound law the primitive fields give way to its ingredients, in stored order (Pull, Swirl, Drag, numbered when a name repeats). Each has a summary ("12 m/s² · masked", "pulsing 0–2") and a Remove button, disabled on a law's last ingredient. Choosing one opens its editor below the list, scrolled into view if it would open below the panel's fold. The editor holds the primitive's parameters; then each gain (Constant or Triangle, with min, max, period and phase, and the value at the current tick); then each mask, outermost first (Box, Sphere or Cylinder, its position and rotation in the law's frame, its dimensions and fade, and a note that it changes where the ingredient acts, not which way it pushes); then Add gain and Add mask. A nested sum shows as a Group and opens in place. Every control is one validated law put and one undo entry, and a refusal names the path and keeps the last valid value. Its fields are named in context ("Drag mask radius"), so none shares an accessible name with the law's own.

There is no reordering control: the stored order is shown and kept, and a reorder would be a semantic edit. The Laws list stays in stable ID order and labels are presentation; `tests/ingredients.test.ts` shows reversing terms changes the bits and the digest, while relabeling, recoloring or hiding laws changes neither.

## Findings

1. **Harness slips in the first M5 runs** (fixed; the app was right each time). In order: the app logged an ingredient's focus change as a `control` event, which followed and hid the edit's own event (the app now logs `ingredient-focus`, which is `82f1e15`); zsh read `[2]` in an unquoted handle name as a glob, and `$original['terms']` inside double quotes as an array subscript; and the script named the saved file without its suffix, which the app correctly refuses (caught before a run reached it). Every run that met one of these was discarded. The counted `m5-compose` run is the last, complete one.
2. **A recording outlived its run** (fixed). One script error ended a run without the harness's `fail`, so its recorder kept running and its full-screen overlay covered the app at the next run's first click. The hit test saw it and refused the input ("topmost is … Terminal"). `m5-compose` now stops a recording on any exit. Informational.
3. **The Scene panel scrolls below its fold** at the built-in display's height (M2 finding 8, M8's). The harness's `reveal` scrolls it with a hit-tested wheel step before clicking a control below the fold, so it never clicks a rect it cannot see. In the app, an opened ingredient editor scrolls itself into view. Informational.
4. **Framing a law with F** zooms until its bounds fill the view. The projected box around the Storm Bottle then reaches under the switch cluster at 1280×800, as any framed law of its size would. The example's own camera keeps the bottle clear, in the stream and beside it. `m5-legible` checks the default view. Informational.
5. **Synthetic drags reach WebKit only in part** (M2 finding 3): every gesture of `m5-compose` committed through the stale-buttons reconciliation, as in M3 and M4. A real trackpad drag of the bottle and of a mask handle is an owner check. Informational.
6. **A short typecheck overlapped P0 run 2** of the pre-review regression `m4-perf` (about 23:42:55–23:43:00; the rerun had nothing beside its timed scenarios). That run's figures equal runs 1 and 3 in every percentile. It is kept, with this note. Informational.
7. **Stricter live validation.** Validating a law now refuses unknown keys on a primitive leaf in memory as well as in a file; before, a live candidate's extra keys were dropped. No accepted path produced them. Informational.
8. **A sum left with one term becomes that term** (changed in review, `9eab04e`; first recorded as kept). Removing all but one ingredient makes the law a one-leaf law again, or makes a group of one into its ingredient. The bits are the same either way, since a sum starts from its first term (tested). Undo restores the earlier tree exactly. Informational.
9. **Kernel identity `affine-ak-v2`.** The field kernel gained operators and a tick input, so its recorded identity changed, as M3's did. The simulation profile, which is scene data, did not. Informational.

10. **The first synthetic click after a recording starts can be lost** (harness; M0 finding 1's class). `m3-demo`'s first Play click, about 2 s after its first recording started, never reached the page in three runs. The hit test passed, the window kept focus, and the app logged no event of any kind. A probe of eight trials reproduced it only on the first recorded trial of a session (two of two), never on later recorded trials (four) or unrecorded ones (two); a throwaway warm-up recording in a separate run did not prevent it. In M4 the same scenario lost a Play click once. In the pre-review counted run the resend was needed once, for the same first Play click; in the rerun on `2a06bad` it was not needed. Informational.
11. **An invisible window of another application** (alpha 0, layer 25, 118×38 pt at the screen's bottom center) is skipped by the hit test, which ignores transparent windows. It covers no Lawsmith control used by the scenarios. Informational.
